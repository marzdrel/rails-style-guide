Style Guides
============

## Git

### How to make commits

- Commit small changes often instead of doing big commits every now
  and then
- Do not mix different issues in single commit
- If you spot any minor style issues while working on a feature commit
  them separately
- Always review changes before commiting to avoid accidental mistakes,
  and/or to avoid random files beeing added to the repository
- Do not rush your commits, review file changes and commit messages
  carefully before submitting
- It's a good practice to run `rspec` and `rubocop` for modified files
  before commiting

### Suggested GitHub flow

- Begin from updating a master branch:

  ```bash
  $ git checkout master
  $ git pull origin master
  ```

- Create a new branch for your new feature. Use task number in the branch name.

  ```bash
  $ git checkout -b TCBK-123-new-feature-branch # use dash-case for a branch name
  ```

- Commit your changes often to allow earlier code review.
After commiting very first changes, push your branch to remote and create a [draft pull request](https://github.blog/2019-02-14-introducing-draft-pull-requests/):

  ```bash
  $ git push origin new_feature_branch
  ```

  ![Github draft Pull Request](https://i1.wp.com/user-images.githubusercontent.com/3477155/52671177-5d0e0100-2ee8-11e9-8645-bdd923b7d93b.gif?resize=1024%2C512&ssl=1)
- PR title should follow the pattern: `[TCBK-xxx] Title of the task`.
For example: `[TCBK-123] Integrates with external API`
- PR description should contain a link to the task in Jira -
template already contains a placeholder for that just add number of task at the end
- When ready, change the status to 'Ready for review'
near the bottom of your pull request to remove the draft state.
- After getting approvals, merge your branch to the `master`.
Use `squash and merge` option on GitHub to keep the flat commit history

### Ignored files

Do not add files related to local development environment to `.gitignore`. It
should only contain entries common for everyone.
<br> If you want to exclude files generated by your specific operating system or editor
use `.git/info/exclude` file instead.

### File name conventions

Do not use upper case letters in file names in general. There is a subtle
difference on how macOS and Linux handle file names. For example, if you
have a file named `MyFile.txt` and you try to rename it to `myfile.txt`
on macOS, it will not change the name of the file. On Linux, it will
rename the [file](file) to `myfile.txt`. This can cause problems when working
with git, because git will treat those files as different files. In general
in typical setup macOS does distinguish between upper and lower case letters
but allows to use both to access the same files.
